1. How /admin/settings works

Every external-service credential (Resend, OpenWA, Meta, Dinstar, Firebase, CRM webhook secret) is admin-configurable here, encrypted at rest (AES-256-GCM), and takes effect immediately with no restart. The only exceptions are telephony-level settings (AMI, Coturn, VM_PUBLIC_DOMAIN) — those stay in .env / pbx_configs/ by design and need a restart.

Live screenshot: /admin/settings showing Email (Resend), WhatsApp (OpenWA), SMS (Dinstar UC2000), OTP, Firebase and CRM Webhooks sections.

Each section has a Test connection button — always click it after saving. It is the fastest way to catch a typo'd key or an unreachable host before an agent hits the same failure live.

2. Email — Resend

Required before any agent invite can be sent.

  1. Sign up / log in at resend.com.
  2. Add and verify your sending domain under Domains (adds a few DNS records — see Section 6 if you are also moving DNS to Cloudflare; do this after the cutover so you only touch DNS once).
  3. Go to API Keys → Create API Key, copy the key (shown once).
  4. In Algo PBX: /admin/settings → Email, paste the key and the verified sender address, then click Test connection.

3. WhatsApp — OpenWA

Required before OTP verification works at all (OPENWA is the default OTP_CHANNEL) and before the WhatsApp chat panel is usable.

  1. Configure the OpenWA connection details (host/webhook secret) at /admin/settings → WhatsApp: OpenWA.
  2. Pair the WhatsApp instance afterward at /admin/whatsapp — this is where you scan the QR code with the WhatsApp number's phone.
  3. Confirm status shows Connected before relying on OTP delivery.

4. SMS & Voice — the Dinstar UC2000

The Dinstar UC2000 is a 4-port GSM gateway that bridges physical SIM cards to Algo PBX two separate ways: a SIP trunk for voice (Asterisk / pjsip.conf) and an HTTP/JSON API for SMS (/admin/settings). Same box, same LAN IP, two integration points — don't confuse them.

4.1 — Physically connect it

  1. Connect the Dinstar's LAN port to your office router/switch with a standard Ethernet cable (or directly to the PC's NIC if point-to-point — but a router/switch is strongly preferred so both the Dinstar and the office PC/VM sit on the same routable subnet).
  2. Insert your GSM SIM card(s) into the port(s) you intend to use (1–4).
  3. Power it on — wait for the LAN/status LEDs to settle (roughly 60–90 seconds for full boot and SIM registration).

Finding its IP address

By default most Dinstar UC2000 units either DHCP an address from your router or ship with a static factory default (commonly 192.168.1.101 or similar — check the label). Two reliable ways to find it:

# Option A — router DHCP client list (usually http://192.168.1.1 or http://192.168.0.1)
# look for a device named "UC2000" or a Dinstar MAC OUI.

# Option B — network scan
nmap -sn 192.168.1.0/24        # Linux/macOS
# or use "Advanced IP Scanner" on Windows

4.2 — Log into the Dinstar's own web GUI

  1. Open http://<dinstar-ip> in a browser on the same network.
  2. Default credentials are typically admin / admin — change this immediately after first login.

The /admin/settings fields (SMS side) are hot-reloaded, no restart. The pjsip.conf value (voice side) is a file on the VM, edited directly and requiring an Asterisk reload:

# On the VM, after editing pbx_configs/pjsip.conf with the Dinstar's real IP:
docker compose exec asterisk asterisk -rx "pjsip reload"
# or, for a full restart:
docker compose restart asterisk

4.4 — If the Dinstar-connected PC isn't on the same LAN as the VM

Use Tailscale subnet routing (from ALGO_PBX_MASTER_DOC.md §6.3) when the Dinstar sits in an office network separate from wherever the Algo PBX VM runs:

# ON THE OFFICE PC (same LAN as the Dinstar):
echo 'net.ipv4.ip_forward = 1' | sudo tee /etc/sysctl.d/99-tailscale.conf
sudo sysctl -p /etc/sysctl.d/99-tailscale.conf
sudo tailscale up --advertise-routes=192.168.1.0/24
# Then: login.tailscale.com -> Machines -> this device -> Edit Route Settings -> APPROVE the route.

# ON THE ALGO PBX VM:
sudo tailscale up --accept-routes
ping 192.168.1.50
curl -I http://192.168.1.50

If the office PC and the VM are on the same LAN, skip Tailscale entirely — DINSTAR_LAN_IP is just its LAN IP.

5. Optional: Meta Cloud API & Firebase

Only needed if you switch OTP_CHANNEL away from OPENWA in the OTP section of /admin/settings.

  • Meta Cloud API — create a Meta developer app, add the WhatsApp product, grab the permanent access token and phone number ID from developers.facebook.com; paste into /admin/settings → WhatsApp: Meta Cloud.
  • Firebase — create a project at console.firebase.google.com, enable Cloud Messaging, generate a service-account key under Project Settings → Service Accounts, paste the JSON into the Firebase section.

6. Domain cutover: GoDaddy → Cloudflare, free SSL

This section is documentation only — nameserver changes affect live DNS and should be done by you directly in your own GoDaddy/Cloudflare accounts. Diagrams below are reference layouts of the current dashboards.

6.1 — Add your domain to Cloudflare first

  1. Sign up / log in at dash.cloudflare.com.
  2. Add a domain, enter the domain you bought on GoDaddy, choose the Free plan.
  3. Cloudflare scans existing DNS records and shows you a list to import — review them.
  4. Cloudflare shows you two nameservers assigned to your domain (e.g. ana.ns.cloudflare.com, bob.ns.cloudflare.com) — copy these for GoDaddy.

6.2 — Change nameservers at GoDaddy

  1. Log into godaddy.com → My Products.
  2. Find your domain, click DNS next to it.
  3. Under Nameservers, click Change, choose Enter my own nameservers (Custom).
  4. Paste the two Cloudflare nameservers from 6.1, remove any GoDaddy-default ones, Save.
Nameserver changes typically take 30 minutes to a few hours, occasionally up to 24–48 hours, to fully propagate. Cloudflare emails you once it detects the change and activates the zone.

6.3 — DNS records in Cloudflare

Once the zone is active, add the A record pointing at your VM:

TypeNameContentProxy status
A@ (or your subdomain, e.g. pbx)Your VM's public IPDNS only (grey cloud) — see warning below
IMPORTANT — PROXY (ORANGE CLOUD) DOES NOT WORK FOR THIS STACK. Cloudflare's proxy only forwards HTTP/HTTPS traffic on a small set of ports and terminates TLS itself. Algo PBX needs raw UDP 5060 (SIP), UDP 10000–20000 (RTP), UDP 20001–30000 (TURN relay), and WSS on 8089 reaching your VM directly — none of that works through the orange-cloud proxy. Set the record to DNS ONLY (grey cloud) so it resolves straight to your VM's IP, and get your TLS certificate a different way.

6.4 — Free SSL: two workable options

OptionHowWhere the cert goes
Let's Encrypt (recommended)Install certbot on the VM, run it against your domain once DNS resolves to the VM's IP. Free, auto-renewing, browser-trusted.pbx_configs/keys/fullchain.pem / privkey.pem (symlink or copy from /etc/letsencrypt/live/<domain>/)
Cloudflare Origin CACloudflare dashboard → SSL/TLS → Origin Server → Create Certificate. Only trusted by Cloudflare's own proxy — since we're running DNS-only, browsers will not trust this for direct connections. Use only if you later proxy the web port through Cloudflare while keeping 8089/5060/RTP on a separate unproxied record.Same paths as above
# Let's Encrypt, standalone mode (stop anything on port 80 first):
sudo apt install -y certbot
sudo docker compose stop web
sudo certbot certonly --standalone -d your-domain.example.com
sudo cp /etc/letsencrypt/live/your-domain.example.com/fullchain.pem pbx_configs/keys/
sudo cp /etc/letsencrypt/live/your-domain.example.com/privkey.pem pbx_configs/keys/
docker compose start web

# Renewal (certs expire every 90 days) — add to crontab:
0 3 * * 1 certbot renew --pre-hook "docker compose stop web" \\
  --post-hook "cp /etc/letsencrypt/live/your-domain.example.com/*.pem /opt/algo-pbx/pbx_configs/keys/"

6.5 — Point .env at the final domain

VM_PUBLIC_DOMAIN=your-domain.example.com
AUTH_URL=https://your-domain.example.com

docker compose down
docker compose up -d

This is one of the few values that lives only in .env and requires a restart — it is not editable from /admin/settings.

7. Final checklist

  • Email (Resend) — connection tested, at least one invite sent successfully
  • WhatsApp OpenWA — instance paired, QR scan complete, status Connected
  • Dinstar SIP trunk — outbound test call placed through a SIM, inbound call reaches the ring group
  • Dinstar SMS API — /admin/settings Test connection passes; a test SMS sent and received
  • GoDaddy nameservers pointed at Cloudflare, zone active
  • DNS A record — DNS-only (grey cloud), not proxied
  • Real TLS cert (Let's Encrypt) installed in pbx_configs/keys/, browser trusts wss://
  • VM_PUBLIC_DOMAIN / AUTH_URL updated in .env, stack restarted
  • Certbot renewal cron job in place
  • Dinstar default admin password changed from factory default
